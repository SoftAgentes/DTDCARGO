## Qué significa cada clase

- **R-D:** runtime que llama directamente una RPC creada por las 32. Sin esa migración pierde la función indicada, aunque capture el error y la pantalla siga renderizando.
- **R-T:** runtime que llama una función que a su vez necesita una RPC nueva de C. Se trazó la función concreta; compartir un módulo con otra función no crea una dependencia ejecutada.
- **R-A:** autónomo respecto de la existencia de objetos nuevos de C. No significa independiente de otros cambios de código, ni validado para integrar, ni ajeno al contrato RLS. Se anotan las policies relacionadas y los cruces de frontera.
- **T / F:** test o fixture, **inerte para usuarios de producción**. Puede importar código que exige la migración o comprobar su contrato mediante mocks. Que pase no prueba existencia de RPC, GRANT, RLS, reconstrucción ni comportamiento autenticado.

Hay **2 R-D + 3 R-T + 14 R-A** entre los 19 de runtime. Un helper R-A que aún nadie importa no produce una funcionalidad visible; su adopción exige también el consumidor modificado. Los tests se clasifican por el comportamiento que verifican, no como pantallas rotas.

### Consecuencias funcionales de un deploy sin RPC

No todas las ausencias provocan crash. `profile-private-context.ts:33-34` devuelve contexto vacío. `payment-report-commands.ts:136-146` devuelve error/resultado incierto y no obtiene recibo. `portal-queries.ts:139-140` devuelve asesor nulo. **`portal-visibility-queries.ts:29-30` devuelve un set vacío ante fallo de RPC0402: muestra todos los hitos**, incluidos los que una regla quisiera ocultar. Un build/contrato con mocks puede estar verde mientras esta degradación cambia lo que ve el cliente. Debe conservarse la secuencia de migración y adopción correspondiente y probar ambos caminos, no declarar la ausencia inocua porque no hay excepción.
